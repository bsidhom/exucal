## Findings

How the model of §1.2.1 for conversion and the output modes holds against the code, section by section.

- **The three output modes and the blank want hold as modelled.** The pipeline reads the `want` in the order Q17 states (`src/core/pipeline.ts:505-549`), a `want` that is a call is an ordinary expression with a reciprocal, and a blank `want` answers in the primitives through `evaluateText` and `dimensionExpr` (`src/outcome.ts:246-274`). One omission in the pages and in Q13: a conversion's ratio is refused not only at the exponent bound but at the significand limit, since `divideBalls` forms an exact quotient only within it (`src/core/ball.ts:829-835`) and `convert` passes a `tooLarge` on (`src/core/convert.ts:190-193`). `3^30000 m` into `5^20000 m` shows it. The code comment at `src/core/convert.ts:132-138` says the ratio is never `tooLarge` there, which is wrong in the same way. (New gap.)
- **The reciprocal line holds, and lives in `src/outcome.ts`, not in the component.** It is one `step` of `1 / value` at the user's context, settled in exact mode and rounded once in decimal mode, pushed only when it succeeds (`src/outcome.ts:323-336`), and every exclusion of Q14 holds: no line for a list, a function, a blank `want`, zero, a value that cannot be told from zero, or any refusal of the quotient, silently. Issue #92 is open; of its three rows, the decimal-mode one is now answered by `step` (`3 m` into `m` gives `m = 0.33333333 × 3 m`, exact), and the page's two remaining gaps, no retry and no words for a refusal, stand. The page says the reciprocal "stays in the component", which `src/unit-converter.ts` is; it stays in the outcome module.
- **Unit lists hold, with two refinements and one gap.** The count rule, the straddle rule, the positive and decreasing checks on the ball and the midpoint, the carry in `roundTerms` with the uncarried fallback, and the zero-term omission are all as Q15 and the page state, and every example reproduces. The refinements: the remainder is rounded at the digits it certifies, the display digits only when it certifies them all (`src/outcome.ts:548-551`), which the page states one sentence after saying "at the display precision"; and with the ratio notation an exact remainder that fits its width is written entire, so nothing is rounded and nothing carries (`src/outcome.ts:552-553`). The gap: a typed list's unit whose ball straddles zero at a pass is `nonpositiveUnit`, which the retry loop never retries (`src/core/pipeline.ts:394-404`), where the same expression as a single `want` is retried as an unresolved `want`. `1 m` into `(1e-30 + approx(1) - 1) m` gives `1 m ≈ 1e+30 × (1e-30 + approx(1) - 1) m`; `1 m` into `ft;(1e-30 + approx(1) - 1) m` is refused as not positive. The code calls this an accepted gap (`src/core/pipeline.ts:93-96`); no page states it. (New gap.)
- **Conversion into a function holds in all six steps.** `convertToFunction` does what `devdocs/functions.md#A function as the want` lists, in that order, and `inverseMismatch`'s criterion is `disjoint`: two exact values compared exactly, otherwise a difference wholly on one side of zero, with a refused difference refuting nothing (`src/core/pipeline.ts:876-882`). The `noInverse` wording the page quotes is the one `src/messages.ts:465` writes. What the pages leave implicit: the inverse, the function applied back and both condition checks run at the operand context of the pass, and the count is stepped at the pass's context. The Display section's "a ratio is written bare inside the call" holds for a plain-number argument (`1 K` into `tempC` with the ratio notation is `tempC(-5443/20)`) and not for an argument with a unit, where the ratio is parenthesized before it as anywhere else (`1 m` into the scratch `bakers` is `bakers((1250/381) in)`); a negative argument is written inside the call (`bakers(-2 in)`).
- **Typeable-back lines and the copy text hold, with one crash at the top edge.** The copy button copies what it is given (`src/copy-button.ts:71-72`, `105-109`), and the converter gives it `copyText(line)` (`src/unit-converter.ts:286`): the printer's text of the same tree the screen renders, with `*` for `×` and nothing else different (`src/core/print.ts:105`). The parentheses follow the grammar's levels, which is how a ratio comes out parenthesized before a unit and bare before `×`, and every form tested pastes back. The crash: a value within the exponent bound whose display rounding carries past it (`9.99999999e1000000000000000000`, alone or into `m`) makes `numberExpr` throw (`src/outcome.ts:394-398`) rather than produce a line, because `parseDecimal` refuses `1e+1000000000000000001`. N12's "one edge literal at the exponent bound does not paste back" understates this. (New gap; a code fix, outside the audit.)
- **The converter section describes a re-parse that does not happen.** The outcome writes each side from the expressions the conversion carries (`haveExpr`, `wantExpr`, a listed unit's `expr`, the parameter's `unit.expr`; `src/core/pipeline.ts:215-250`) and parses the `have` again only for a blank `want` (`src/outcome.ts:380-384`); the printer decides the parentheses. Two passages say the `want` is parsed again, tagged above.
- **The relation and the notes hold.** `=` when every shown value is exact, the uncertified sign in decimal mode, `≈` otherwise (`src/outcome.ts:372-377`); the notes are worded as the page quotes them (`src/outcome.ts:504-517`); an undecided condition makes every line `≈` and adds one warning per distinct condition (`src/outcome.ts:224-234`). The defaults the page names, eight digits and half even, are `src/core/context.ts`'s exported defaults as the harness printed them. The note wording "are certain" is the one §12, question 8 changes to "certified", a code change recorded for unit A2; the page quotes the code and follows it.
- **The examples reproduce**, in all four pages, with two caveats. `docs/definitions.md#Unit lists` writes `8 min/mi + 34.285714 s/mi` where the app writes `8 min / mi + 34.285714 s / mi`, the printer's canonical spacing (`src/core/print.ts:106`). The `dozen` of `devdocs/functions.md#Display` is the page's own running definition (`devdocs/functions.md:32-33`), not the file's: `src/units.txt:614` defines `dozen` as a unit, so `2 ft` into `dozen` against the app is a mismatch, not `dozen(2 in)`, and the file has no function with an annotated parameter and an inverse to put in its place.
- **`docs/README.md#(top)` holds fact by fact** (the two answers, the reciprocal line and its absence for a list, the copy text `36 in` and `0.027777778 * 3 ft`) and frames the app as a converter "in the spirit of GNU units", against §12, question 2, which has the calculator lead and calls out GNU units only where it helps a user onboard. The proposed edit below reframes the opening paragraph; the page's index list is the business of the unit that revises `docs/README.md` to the map of §7.1 (§12, question 18).

### `docs/definitions.md#Unit lists`

The complete section, with the fields' names (§8: have and want), the display digits, and the spacing the app writes:

"The want may be a list of units separated by `;`, largest first, and the answer is then a sum: a whole number of each unit but the last, and the rest in the last. `1 m` in `ft;in` is `3 ft + 3.3700787 in`, `3661 s` in `hr;min;s` is `1 hr + 1 min + 1 s`, and `1 hr / 7 mi` in `min/mi;s/mi` is `8 min / mi + 34.285714 s / mi`. A unit that would get a count of zero is left out (`3601 s` is `1 hr + 1 s`), a negative quantity gives negative terms (`-3 ft - 3.3700787 in`), and the line is written so that it can be typed back as a have. Each item is any expression, so `ft;in/8` counts eighths of an inch. The rest is shown rounded to the display digits as any answer is, and when that rounding would reach a whole of the unit before it, the sum is rounded as a whole instead: `2.9999999999 ft` in `ft;in` is `3 ft`, never `2 ft + 12 in`.

The units of a list must all convert to the have, must be positive, and must decrease along the list (`in;ft` is an error, as is `ft;12 in`). A list is an output form only: it can be typed as the want, never as the have.

A list can be defined under a name in the definitions file, as `time` is (`time  hr;min;s`), and that name typed alone as the want means the list. The name lives among the unit names, so it cannot also be a unit, and it may not read as a prefix followed by a unit either (`ms` could not name a list, because it means milliseconds): unlike a unit's name, a list's name only means anything as the want, and the same text should not mean different things in the two fields. A list's name is not a unit anywhere else: `2 time`, or `time` in a list or in a definition, is an unknown unit. The file checks a defined list by the rules above when it is loaded, so that a defined list can fail only for not matching the have."

(The rules on a list's name in the file and the check at load time are the build's, verified by unit A9 or D3; this unit verified the rest.)
