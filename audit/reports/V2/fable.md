### `devdocs/architecture.md#Definitions`

The complete pared section:

System units are not special: they live in a static definitions file, `src/units.txt`, that is bundled into the app as an asset of its own (a URL import, so it is emitted beside the scripts and precached with the rest of the build, and fetched when the app starts) and go through the same parser as any other definitions. `buildTable` takes one list of definitions, so that user definitions, once the app has a way to enter them, are appended to the system ones; today only the system file is loaded. `src/units.test.ts` builds the system file and checks a sample of conversions from each of its sections.

The format, the six kinds of definition and what the system file contains are the user's: [docs/definitions.md](../docs/definitions.md) states them, and [docs/expressions.md](../docs/expressions.md) how a name is read. This section covers what the core does with a definitions file.

`parseDefinitions` reads one definition per line and returns them in the order written, duplicates included, knowing nothing about what they mean. What it keeps beside the tree matters later: a unit list's items, a parameter's and a result's annotations and a function's conditions are kept with the text they were written as, since that text is what the UI shows beside a term, inside a recovered argument's call or in a message that quotes a condition, and the table has no other way to get at it. The whitespace after a unit's or a prefix's name is required, so that `inch2.54 cm` is an error rather than a definition of `inch2`. The parser rejects, each where it is written: an annotation with a number other than `1`, which would read as a scale that conformance ignores (`annotationScale`); an annotation that is a sum, a difference, a negation or a call, which names no unit (`annotationNotUnits`); an annotation on an inverse's parameter, whose dimension is its function's result's (`inverseAnnotation`); a parameter named twice (`duplicateParameter`) or named like a unit its own head's annotations use (`parameterNamesUnit`); a condition whose comparisons do not all point one way, `0 < x > 1` (`mixedComparison`); and a `[` after a function's name, reserved for dimension variables (`unsupported`). Every span is an offset into the whole text, not the line: a definition carries the span of its text from name to body, for the errors `buildTable` reports against a definition as a whole, and the spans inside its body serve the errors within it.

`buildTable` evaluates each body to a quantity, resolving references on demand with memoization and a visiting set, so definitions may appear in any order and cycles are reported rather than looped on. The result is the unit table: the primitives with their roles, the prefixes with their factors (a prefix's body must be dimensionless, with neither a dimension nor a kind), the units with their quantities, the unit lists and the functions, each a map keyed by name in declaration order. The primitives are among the units, as quantities of one of themselves, so that a lookup is one map read. The primitives with their roles are collected from the definitions before any body is evaluated, because a body that is a sum needs them to check its operands, and a body may refer to a primitive declared after it.

The name rule is the reference's; here it is applied twice. Prefixes are a namespace of their own, and everything else (primitives, units, unit lists, functions and the built-ins) shares one, so a list or a function named like a unit is a duplicate. The build applies the rule over definitions before any quantity exists, so `names.ts` is generic in what a prefix or a unit maps to, and the finished table applies it over quantities. A call's name resolves among the functions and the built-ins exactly, so `ktempC(1)` is a call of nothing (`notAFunction`), and the build rejects a list's, a function's or a built-in's name that would read as a prefix followed by a unit: a list's name means the list only as a bare `want`, while a unit's name means the unit everywhere, so `ms` as a list's name would make one text mean two things in the two fields, and a function's name would mean the function as a `want` and a prefixed unit as a `have`.

The table's lookup forms a prefixed unit as the prefix's factor times the unit's quantity, under the context the lookup is given, and assumes the product is never refused: the file's prefixes and units are nowhere near the exponent bound, and the product's size is held to the significand limit by the node that names the unit, not here. A lookup has no error to return for a refusal, so the one case that could reach it, a definition that puts a unit within a prefix's factor of the bound, throws (`table.ts`). That is the one place the core's rule on exceptions is knowingly not met; the error kind it needs belongs with the editor for user definitions, the only way such a unit can be written.

Unit lists are not units: no expression can refer to one, so they stay out of the walk, and each is evaluated in its place in the order, item by item, through the same lookup a body uses, requesting what it refers to from the top of the walker (which can never close a cycle). A list's units are checked as `convertToList` checks any list, against the first of them, so that a defined list can fail to convert only for not conforming to the `have`. The table holds each list as its units with their texts, apart from the units.

A function can be referred to, by a call in any body, so it is a node of the walk, and evaluating it means checking it ([functions.md](functions.md), "Build-time checks"): its annotations are evaluated and must exclude zero, since a recovered argument is written as a count of the parameter's; its body's dimension is taken without evaluating it (`dimension-of.ts`), with each parameter bound to its annotation's dimension (dimensionless without one), through the walk's own lookup, and is the function's result, checked against the result's annotation when there is one; and each condition's terms are taken the same way, each conforming to the next, and each condition must mention a parameter. A call in a condition is a dependency of the walk as one in a body is. A unit may then be defined by a call (`boiling  tempC(100)`), a function's body may call another, and a cycle through a function is reported like any other. An inverse is keyed by its function's name apart from every namespace, and nothing can refer to it, so, like a list, it stays out of the walk and is checked in its place in the order, requesting its function from the top, which lets it call its own function: its function must have exactly one parameter, and its body's dimension, with its own parameter bound to the function's result, must conform to what that parameter takes, its conditions checked as a function's are. The table holds each function as its body, still an expression, with its parameters in order, each with the unit it takes and its text, its result's dimension, its conditions with the parameters each mentions, and its inverse when one is defined: a call evaluates the body afresh, through the table's lookup. The table is built at the ceiling, where no later pass could decide a condition, so a unit, a list's unit or an annotation that calls a function whose condition is left undecided fails the build: a unit has nowhere to carry the warning.

Every name is known once the table is built, so ambiguity is a property of the table rather than of the input, and `buildTable` checks for it. A name with two different prefix-unit splits (`d`+`am` against `da`+`m`, were `am` a unit) is a build error, so a table that builds has at most one split per name. A unit name that is also a valid split (`min`, the minute, against `m`+`in`) is allowed, because real unit conventions are full of them, and the exact name wins. The check is cheap: for each pair of prefixes where one extends the other, one map lookup per unit that starts with the extension, found in an index of the unit names, which for most extensions (`icro`, `eci`) is no unit at all.

Building is five modules. `table.ts` holds the `UnitTable` itself and the lookup over it that the evaluator resolves user input against. `names.ts` holds the resolution rule and the ambiguity check; `name-index.ts` is the index the check searches, the names sorted so that those starting with any text are one contiguous run. `graph.ts` is the on-demand evaluation: a walker takes a function that computes a node's value given a way to request the values of the nodes it depends on, and memoizes each result; a request for a node whose evaluation is in progress is a cycle, and the walker returns it to the requester, which knows where the request came from. Nothing in it knows what a definition is. `build.ts` puts them together in a fixed order: index the definitions by name, rejecting a duplicate; reject an inverse of no defined function; check the index for an ambiguous name, and the names of the lists, the functions and the built-ins for one that reads as a prefixed unit; collect the primitives and their roles; then walk every definition in order, where a body is evaluated by `evaluate` against a lookup that resolves each name through the index and requests the definitions it means from the walker, with those primitives. The first failure ends the build.

A build error (`BuildError` in `build.ts`) is one of: a duplicate name, carrying both definitions, or the built-in's name and the definition that takes it; an ambiguous name with its two splits; a unit list, function or built-in whose name reads as a prefix and a unit, carrying the definition (or the built-in's name) and the split; a lookup failure at its reference (an unknown name, a function used as a unit, a call of what is not a function, or a prefix times a unit refused as too large or too small); a cycle, carrying the definitions on it in order and the span of the reference that closed it; a prefix whose body has a dimension or a kind, carrying the definition and the dimension; a unit list whose units do not make a list, carrying the definition and the list error with the index of the unit at fault; a function whose body does not conform to its result's annotation, or an inverse whose body does not conform to what its function's parameter takes, carrying the definition and the mismatch; an inverse of no defined function; an inverse of a function with other than one parameter, carrying how many it has; a function whose parameter's or result's annotation is zero, or cannot be told from zero; a condition whose adjacent terms do not conform, carrying the condition's span, the two terms' spans and the mismatch; a condition that mentions no parameter, so that it could only always hold or never; a condition of a call in a unit's, a list's or an annotation's body left undecided at the ceiling; or an arithmetic failure from the evaluator, located as the evaluator locates it. Every span is an offset into the whole definitions text, and a definition's span covers its text from name to body, so each error points at something the user can see.

### `devdocs/architecture.md#Expressions`

The complete pared section:

One grammar serves both definition bodies and user input, so anything that can be typed can also be defined. The language, its precedence and the rules for `-` and for calls are the user's: [docs/expressions.md](../docs/expressions.md) states them. This section is about how the grammar is parsed and what the tree holds.

The grammar's levels of binding and its binary operators are data in `src/core/expr.ts` (`LEVELS`, `BINARY`): the two left-associative levels of the parser (`+` with `-`, and `*` with `/`) are built from the table, and the printer, `src/core/print.ts`, writes a tree back by it, so the two cannot disagree. Juxtaposition is its own rule of the grammar, binding tighter than `*` and `/`, and its own operator in the tree, `juxtapose`: the evaluator treats it as `*`, and the tree keeps it apart so that the printer can write `2 m` back as it was read. A number may only be the first factor of a product, since juxtaposition means "this many of these units" or a product of units; multiplying numbers is written with `*`. The precedence follows GNU units.

The tree has six kinds of node: a number, a unit name, a binary operation (a sum, difference, product, quotient or juxtaposition) of two subtrees, a negated subtree, a subtree raised to a rational exponent, and a call. A number is never negative in the tree: `-2` is the negation of `2`. A number node keeps the text it was read from, so that `1e3` is written back as `1e3` and not `1000`, and a call is the name, with its own span, and its arguments. Every node carries the span of text it came from, so an error found later in the pipeline (an unknown unit, a dimension mismatch) can point back at the input. `parseExpr` knows nothing about units, and `evaluate` knows nothing about text.

Three decisions of the parser are not visible in the language. The parser decides a call by the text alone, since it cannot ask the table whether a name is a function: no space before the `(` makes a call and a space makes a product, so `kg(m/s)` is a call of `kg`, which the evaluator rejects with a message that shows the product with the space. That is the one whitespace-sensitive rule in the grammar; [functions.md](functions.md) ("Alternatives considered") weighs the alternative. An exponent is never an expression, so it is known at parse time; it travels in the tree as the two literals the parser read, undivided (`Exponent`), each checked to be formable within the hard bound and a zero divisor rejected, both read off the literals with nothing formed, and the evaluator takes the quotient where the significand limit applies (`reduceExponent`). The parser has no context to bound a reduction by, and Euclid's gcd on two literals at the hard bound is far too slow to run on every keystroke. And a unit name is taken as long as it goes (`m2` is one name rather than `m` beside `2`), with whether it means anything left to the table. Whitespace is spaces and tabs, never a newline, because a definition body is one line.

A unit list, `ft;in`, is one or more expressions separated by `;`, and is not an expression: `;` binds looser than anything and cannot appear inside parentheses. `parseUnitList` reads one, and `expr.ts` exports the list grammar over any item parser, since the definitions parser wants each item with its text. The comma appears nowhere in the grammar but between a call's arguments, and how many arguments a function takes is the evaluator's to check, not the parser's.

The printer's text is canonical: one space between juxtaposed factors and around the other operators, a quotient of two literals tight as a fraction, and the fewest parentheses that read the tree back as it is, which `levelOf` and the levels decide position by position; one rule the levels do not express, that a number cannot follow a factor by juxtaposition, parenthesizes a right operand that leads with a number. The printer never changes a tree. Its output is pieces, each saying what it is (a number, a name, an exponent, a symbol), so that the converter can style a result's numbers apart; `text` joins them, and the product written with `*` is the one glyph the screen (`×`) and the clipboard (`*`) differ on. A property test prints random trees (`src/testing/expr.ts`) and parses them back, and `formatDimension` is the printer over a dimension built as an expression (`dimensionExpr`). `ParseError` comes from the parsing toolkit below, which both parsers are built from; `Span` has its own small module, because it is not a parsing concept but the vocabulary every later stage uses to locate its errors.

### `devdocs/architecture.md#Unit lists`

The complete pared section:

What a unit list is, what it answers and the rules its units must meet are the user's: [docs/quantities.md](../docs/quantities.md) states them. `convertToList` is the second output mode, over the same conformance check as `convert`, and this section is its mechanics.

The units are checked in order, each for conformance with `have`, for a positive magnitude whose ball excludes zero (a unit that cannot be told from zero is no size to count by), and for being smaller than the one before it by midpoint; the first failure is reported with the index of the unit at fault, so that a message can quote it. The counts are taken from the midpoints, so a count is an exact integer and never `unresolved`: each unit but the last gets the integer count of it that fits in what the earlier units left, truncated toward zero so that every term has the sign of `have`, and the last gets the remainder, the ball `have` less the counted units, computed with the ball operations, so that the terms times the units add up to `have` exactly when everything is exact and contain it otherwise. A ratio whose ball straddles an integer, as `turn / deg` does once both carry `pi()`'s radius, counts as that integer rather than its truncation, so that the remainder is a ball around zero, which the display leaves out, rather than a whole of the unit (`≈ 360 deg`, not `359 deg + 60 arcmin`). A ratio whose integer part cannot be formed within the significand limit (`1e999999999 m` into `ft;in`) is counted as its midpoint settled toward zero at the working digits, still an exact integer, and the remainder is what that count leaves; a count whose ratio falls below the exponent bound is zero, nothing of that unit fitting in what is left (`1e-999999999999999999 s` into `hr;min;s`). Any other refusal of a count, of a count times its unit, or of the difference it leaves, and an `unresolved` of them, is the list's failure, which the pipeline reports as the conversion's, as it reports a refused ratio (`3^32767 m` into `ft/7^21845; in/7^21845` is `tooLarge`, its remainder not aligning within the significand limit).

The terms are exact for exact quantities, as the ratio `convert` returns is, and rounding them for display is more than rounding each: a remainder of `11.9999999988 in` shown at eight digits is `12 in`, which beside `2 ft` reads wrongly. So `roundTerms` is the display rounding that goes with the sum: it rounds the remainder's midpoint to the display precision, in the display's rounding mode, as `roundTo` does, widening its radius by the rounding's shift so that the rounded terms still contain `have`, and, when that changes it, takes the counts again from the rounded sum, so that a remainder which rounds up to a whole of an earlier unit carries into it, through as many units as it must (`3599.9999999999 s` in `hr;min;s` is `1 hr`; under `floor` nothing rounds up, and it stays `59 min + 59.999999 s`). That is one rounding of the whole sum, by less than a unit in the last digit of the remainder, and the second decomposition is exact. The counts are integers and are left alone; one too long for the display is the display's to round, as any value is. When the remainder is already exact at the display precision, the terms come back as they are, and so do they, uncarried, when rebuilding the total from the rounded terms fails, since the display calls `roundTerms` and the uncarried terms still contain `have`: the carry's rebuilt total can pass the exponent bound where the terms did not.

The pipeline reads the `want` as a unit list, of which an expression alone is a list of one. One item that is the bare name of a list in the table means that list, with the texts of its units from the definition; one that is the bare name of a function means the function ("Functions" below); any other one item is a unit and goes through `convert`; two or more items are a list typed out, each evaluated as an expression and paired with its text, sliced from the `want` by its span. A unit of a typed list that fails the list's checks is reported with the texts of all of them, so that a message can quote the one at fault; a list from the table passed those checks when it was built, and can fail only for not conforming to the `have`, which is reported as the mismatch of the pair, as for a single `want`, so that the message quotes the name the user typed.
