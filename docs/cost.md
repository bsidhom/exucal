# The costliest expressions

Status: the catalogue of stage 8 (docs/calculator-plan.md, task 8.3,
under D25). It lists the costliest inputs the cost search has found,
what each pays for, and the issue that would make it cheaper. Runs of
the search add to it over time; the table below is regenerated by each
run, and the prose around it is revised by hand when a run changes the
picture.

The catalogue is the target for two kinds of work. Making the kernels
cheaper takes a case off the list or moves it down; keeping the
interface responsive whatever an evaluation costs (#118, with #119 to
#121) is measured against the same cases, since they are the ones that
freeze it today. Neither is part of the plan: the plan finds and records
the costs, and the issues named below carry the work.

## How a case is measured

A case is a `have` text, a `want` text and the settings panel's
settings. The harness (bench/stress/harness.ts) measures what the
converter runs on each keystroke, `outcomeOf`, in wall time:

- **Cold** is the first evaluation in a worker of its own, whose memos
  are empty but whose unit table is built, as the app builds it at
  startup. It pays for what is computed once: the constants at a new
  ceiling, the Bernoulli run the Gamma family's series take.
- **Warm** is the same case evaluated again in that worker. It pays for
  every pass alone, and is what a keystroke costs once a session has
  seen the case.
- **Passes** is how many passes of the retry loop the warm evaluation
  ran. Every case here runs the whole schedule to the ceiling, since
  its value never certifies: nine passes at the default settings, eleven
  at the highest cap the default range limit allows.
- **Typing** is the case typed out a keystroke at a time, `outcomeOf` on
  every prefix of the `have` in order, in one worker so that the memos
  carry over as they do in a session. The slowest keystroke is usually
  the last, the one that completes the expression; a prefix that never
  certifies costs as much as the whole.

The catalogue ranks the cases by their warm cost per costly call, so
that an expression of many calls does not outrank the call that makes
it costly. Only cases whose warm cost reaches a second are kept, so that
an entry stays among the costliest when measured again: on one machine
the noise is milliseconds. The timings are those of the machine the
search ran on, which each entry in bench/stress/catalogue.json names;
on another machine only their ratios compare, which is what the stress
suite reports.

## Reproducing a case

Each entry in bench/stress/catalogue.json records where it came from:
the seed and index that drew it, or its place in the fixed enumeration.
`pnpm stress:search --seed <seed> --cases <n>` replays a run, and
`--list` prints the cases a seed draws without evaluating them. The
runs log which indices each merge took. Typing
the `have` into the converter, with the entry's settings, reproduces the
cost a user meets. `pnpm stress` measures every entry again, and fails
only if one gives a different value or passes its deadline.

## What the costs come from

Every case in the catalogue has a value that never certifies: an exact
cancellation (`f(a) - f(a)`), an identity (`erf(x) + erfc(x) - 1`), an
edge (`floor` of a value on an integer), or a condition left undecided.
Such a value runs every pass of the retry loop up to the ceiling. Its
cost is the passes times the cost of its costliest call at the last
pass, and the last pass, at the ceiling, outweighs all the earlier ones
together. A value that certifies stops at the first pass that settles
it, so it costs milliseconds. Exact cancellation is not a contrived
case: `beta(0.5, 0.5) - pi()` (#117) is one, and so is any expression
that subtracts a quantity from itself by a longer route.

The causes, costliest first, at the default settings (a ceiling of
4,040 digits):

- **The incomplete beta function**, 0.7 to 6 s a call (#150). Its series
  takes about `bits ln 2 / ln(1 / x)` terms, several thousand at the
  ceiling for `x` near a third, and each term costs a full-precision
  division. Exact parameters cost as much as inexact ones. These cases
  head the catalogue.
- **`erf`, `erfc` and the incomplete gamma functions**, 0.5 to 1.5 s a
  call at a moderate argument and about 3 s at a large one (#149):
  `erfc(-40.5)`, `lowergammareg(500, 2500.25)`. They have the same
  shape, a term count that grows with the bits and a full-precision
  division per term. The large arguments are the regime of #107.
- **The Gamma family at an inexact argument**, 0.5 to 2 s a call:
  `digamma(approx(1/3))`, `beta(approx(1/3), e)`, `gamma(cosh(…))`. A
  wide argument is shifted up through a rising factorial before the
  Stirling series; #125 would make the shift cheap. The cold run also
  pays for the Bernoulli run at the new ceiling, several seconds at the
  defaults and about a minute at the highest cap (#103, #121). A short
  exact argument costs about half as much (`beta(0.3, 7)`, 0.8 s a
  call): its shift is exact.
- **The elementary functions** are cheap at the defaults: the stress
  suite's reference case, `exp(1) - exp(1)`, takes tens of
  milliseconds, and no elementary case reaches the catalogue's
  one-second floor. They become costly only at a far larger ceiling
  (#152).

The memos help only the first run. The constants and the Bernoulli
numbers are memoized, but no function's value is. So a warm run costs
about what a cold one does, except in the Gamma family, whose cold run
also builds the Bernoulli numbers.

Typing tells the same story from the user's side. Of the 6,316
keystrokes that typing out the enumeration's 95 cases took, exactly 95
took 100 ms or more: the last keystroke of each case. Every prefix
before it is either incomplete, an error found at once, or a value
that certifies at the first pass: `incbeta(0.3, 7, 1/3)` alone has
nothing to cancel. So the interface freezes once per
expression, on the keystroke that completes it, for the case's whole
cost. That keystroke is the one #118 has to keep responsive.

## The hangs

Some cases run past the harness's two-minute deadline. The catalogue
keeps them apart, in `hangs`, each with the issue that tracks it, and
`pnpm stress` lists them without running them. Two settings produce
them. Both raise the ceiling, and none of these cases hangs at the
defaults.

- **The highest digits cap under the default range limit** (2,453
  digits, a ceiling of 9,852): the Gamma family at an inexact argument,
  the incomplete beta function, and the incomplete gamma functions at
  an inexact or large argument. All are #151, and the causes above
  apply at two and a half times the digits.
- **The hard bound** (`LIMIT_BITS`, a ceiling of 157,816 digits): the
  special functions by the pass at 18,432 or 36,864 digits, and the
  elementary functions too,
  e.g. `cosh(2.5)^2 - sinh(2.5)^2 - 1` in its pass at 147,456 digits.
  This is #152. Each step of `expFixed`'s series gains a fixed eight
  bits, and the series is summed term by term.

The defaults stay as they are (D25 in docs/calculator-plan.md). These
settings are a user's to choose, and the response to them is the
interface's (#118, with #120's workers), helped by whatever the kernel
issues above make cheaper.
